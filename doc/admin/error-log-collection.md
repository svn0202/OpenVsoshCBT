# Сбор и разбор ошибок в журналах

Цель — получить воспроизводимый срез за выбранный период, найти причины ошибок
и отдельно установить, сохранились ли ответы участников. HTTP-код сам по себе
не доказывает потерю ответа; HTTP 200 не исключает ошибки PHP или БД.

Процедура не требует локального Docker. Журналы читаются на действующих серверах,
анализ выполняется по сохранённым копиям. Команды ниже — шаблоны: имена узлов,
контейнеров, служб и пути журналов берутся из **закрытого** описания установки.

## 1. Зафиксировать период и место хранения

На рабочем компьютере создайте каталог **вне репозитория**:

```sh
umask 077
LOG_CASE="$HOME/Private/OpenVsoshCBT-logs-$(date -u +%Y%m%dT%H%M%SZ)"
mkdir -p "$LOG_CASE"
chmod 700 "$LOG_CASE"
python3 - <<'PY' > "$LOG_CASE/window.txt"
from datetime import datetime, timedelta, timezone
end = datetime.now(timezone.utc).replace(microsecond=0)
print('START=' + (end - timedelta(hours=3)).isoformat())
print('END=' + end.isoformat())
PY
cat "$LOG_CASE/window.txt"
```

Используйте эти **одни и те же** границы во всех источниках, а не «три часа назад»
заново при каждом чтении. Для итоговой выборки удобно правило `START <= время < END`.
Запишите в закрытый `manifest.md`:

- начало и конец UTC, часовой пояс приложения и БД, время на каждом сервере;
- версию приложения/образа, активный слот, время переключений и перезапусков;
- источник каждого файла, время получения, способ отбора и результат команды;
- недоступные источники, ротацию, обрезанные строки и иные пробелы покрытия.

JSON-события приложения используют UTC. Файловые ошибки PHP и даты ответов в БД
могут использовать локальный часовой пояс приложения. Сначала установите его,
затем переводите время; не сравнивайте строки дат с разными часовыми поясами.

Сырые журналы могут содержать логины, IP, URL, идентификаторы участников и запросов.
Не добавляйте их, выгрузки БД, HAR и отчёт обследования в публичный Git. Не включайте
логирование тел ответов, паролей, cookie, сессий или CSRF-токенов для этой процедуры.

## 2. Собрать все уровни обработки запроса

| Источник | Что брать | Для чего |
| --- | --- | --- |
| Внешний nginx | Корреляционный access log и фактический error log сайта | HTTP-код для браузера, время upstream, причина 502/обрыва |
| Apache на хосте, если используется | Access/error logs | Ошибки промежуточного прокси |
| Контейнеры приложения | stdout/stderr всех слотов, обслуживавших выбранный период | HTTP-запросы, PHP, события сохранения и авторизации |
| Файлы ошибок приложения | `public/log/tce_errors.log`, `admin/log/tce_errors.log` | Ошибки, которые могут не попасть в stderr |
| systemd и ядро | События служб приложения/прокси, OOM и остановки | Связь с рестартами и нехваткой ресурсов |
| БД | Только метаданные выбранных попыток/вопросов | Проверка результата сохранения |

Пути nginx определяются действующей конфигурацией `access_log`/`error_log`, включая
наследование из `http` и `server`. Журнал похожего соседнего домена не заменяет
журнал нужного сайта. Полный вывод `nginx -T` храните только приватно, если он нужен.
Для файловых журналов захватите также ротации, пересекающие интервал, включая `.gz`.

Пример на **сервере приложения**: замените значения границ на полученные выше,
а имя контейнера — на настоящее. Выполняйте Podman от владельца контейнеров
(для rootful-установки — через `sudo -n`).

```sh
umask 077
START='2026-01-01T09:00:00+00:00'  # заменить
END='2026-01-01T12:00:00+00:00'    # заменить
LOG_REMOTE="$HOME/private-log-case"
mkdir -p "$LOG_REMOTE"
chmod 700 "$LOG_REMOTE"
APP_CONTAINER='replace-with-container-name'
podman logs --timestamps --since "$START" --until "$END" "$APP_CONTAINER" \
  > "$LOG_REMOTE/container.log" 2>&1
printf 'container log exit code: %s\n' "$?"
```

Повторите для второго слота и остановленных контейнеров, если они работали в этом
интервале, с отдельными именами выходных файлов. Перед удалением старого контейнера
сохраните его журналы: файловые ошибки могут находиться только внутри него.
Не используйте `logs -f` для конечного среза.

Для небольших файлов ошибок можно сохранить полную копию, а затем выделить период:

```sh
podman exec "$APP_CONTAINER" cat /var/www/html/public/log/tce_errors.log \
  > "$LOG_REMOTE/public-errors.log" 2> "$LOG_REMOTE/public-errors-read.err"
printf 'public error log exit code: %s\n' "$?"
podman exec "$APP_CONTAINER" cat /var/www/html/admin/log/tce_errors.log \
  > "$LOG_REMOTE/admin-errors.log" 2> "$LOG_REMOTE/admin-errors-read.err"
printf 'admin error log exit code: %s\n' "$?"
```

Для больших файлов отбирайте записи по времени на сервере, сохраняя многострочные
сообщения целиком. `tail -n 1000` не гарантирует покрытие трёх часов. Ошибка чтения
или отсутствие файла — это недоступный источник, а не «ошибок нет».

Пример ограниченного чтения systemd, также на сервере приложения:

```sh
APP_UNIT='replace-with-unit.service'
# GNU date на Linux: journalctl не всех версий понимает ISO 8601 с T и +00:00.
JOURNAL_START="$(date -u -d "$START" '+%Y-%m-%d %H:%M:%S UTC')"
JOURNAL_END="$(date -u -d "$END" '+%Y-%m-%d %H:%M:%S UTC')"
sudo -n journalctl -u "$APP_UNIT" --since "$JOURNAL_START" --until "$JOURNAL_END" \
  --utc --no-pager -o short-iso-precise > "$LOG_REMOTE/service.log"
sudo -n journalctl -k --since "$JOURNAL_START" --until "$JOURNAL_END" \
  --utc --no-pager -o short-iso-precise > "$LOG_REMOTE/kernel.log"
```

При драйвере логирования `journald` для проверки тишины старого слота используйте
курсор `journalctl -u "$APP_UNIT" -n 1 --show-cursor --no-pager` и отсутствие
активных соединений к старому порту. Не полагайтесь только на `podman logs --tail 1`:
чтение большого журнала может задержаться. Исходный systemd journal сохраняется
после удаления контейнера в пределах настроенного срока хранения.

Один контейнер может попасть в journal дважды: через драйвер Podman
(`_TRANSPORT=journal`, поле `CONTAINER_NAME`) и через stdout службы. Для подсчёта
событий выбирайте один источник, например
`journalctl "CONTAINER_NAME=$APP_CONTAINER" --since "$JOURNAL_START" --until "$JOURNAL_END" -o cat --no-pager`.
Наличие поля проверьте через `journalctl -o json` в закрытой выборке; отсутствие
записей по фильтру не означает отсутствие ошибок. Не складывайте эту выборку
с `podman logs` того же контейнера.

Аналогично соберите службы прокси. Для access/error log nginx и хостового Apache
сохраните нужный период из действующих файлов и ротаций. У разных форматов разбор
дат различается: простой `grep` по часу не подходит для окна через полночь.
Перенесите файлы по SSH/SCP в локальный закрытый каталог; зафиксируйте размеры,
контрольные суммы SHA-256 и ошибки команд. Не копируйте многогигабайтные журналы
целиком, если можно получить полный ограниченный срез.

## 3. Построить сводку без двойного подсчёта

На каждом уровне отдельно посчитайте число запросов, коды, методы, пути и задержки.
Сначала выделите 5xx, отказы сохранения, конфликты версий, ошибки PHP/SQL и 404.

В журнале контейнера могут одновременно быть обычные combined-строки Apache
и строки вида:

```text
request_id=... application_request_id=... method=POST path=... status=200 duration_us=...
```

Считайте запросы по **одному** формату, иначе получите дубли. `duration_us / 1000`
даёт миллисекунды; это время сервера, а не полная задержка в браузере. Для сравнения
используйте число запросов и p50/p95/p99, отдельно по сохранению и другим маршрутам.

События приложения:

- `[openvsosh.auth]` — вход, отклонение сессии/CSRF; [описание полей](authentication-log.md);
- `[openvsosh.answer]` — результат обработки API сохранения;
- `[openvsosh.answer.write]` — результат операции записи, включая повторы и отказы;
- `[openvsosh.answer.final]` — результат финального сохранения формы.

Несколько каналов одного запроса не являются несколькими сохранёнными ответами.
Группируйте по `request_id`, затем по `testlogid`, `operation_id` и версиям.
Повтор одного `operation_id` может успешно вернуть уже сохранённую версию.

Для `csrf.rejected` и `session.rejected` дополнительно сравнивайте категории:

- `session_cookie_valid`, `session_cookie_count`, `session_id_matches_cookie` —
  допустим ли формат cookie, сколько одноимённых cookie передано и принят ли этот ID;
  `null` в счётчике означает отсутствие доступного заголовка Cookie;
- `session_read_status` — `loaded`, `empty`, `missing`, `expired`, `db_error` или
  `not_read`; состояние фиксируется при чтении, до дальнейшей авторизации;
- `session_context_kind` — `stable`, `v1`, `legacy`, `unmatched` или `missing`.
  `unmatched` не позволяет определить поколение несовпавшего хеша.

Наличие cookie не доказывает наличие серверной сессии. Совпадающий контекст не
доказывает валидность CSRF: токен также привязан к ID сессии и скрипту. Сначала
сопоставьте отказ с получением свежей формы и последующим входом; не принимайте
отклонённый POST автоматически. Значения cookie, ID сессий и токенов в эти
категории не включаются.

После JSON Apache может дописать `, referer: ...`. Поэтому `json.loads()` всей
оставшейся строки отвергнет корректное событие. Кроме того, Apache экранирует
обратные слеши и может записывать байты UTF-8 как `\xHH`. Сначала снимите **один**
слой экранирования Apache, затем разбирайте JSON. Иначе кириллица даст ошибку,
а пути и User-Agent могут незаметно получить лишние слеши. К исходному JSON без
обёртки Apache это преобразование применять нельзя. Пример извлечения событий из уже
собранного среза контейнера (на рабочем компьютере):

```sh
python3 - "$LOG_CASE/container.log" > "$LOG_CASE/events.jsonl" <<'PY'
import json, re, sys
pattern = re.compile(r'\[openvsosh\.(auth|answer(?:\.[a-z_]+)?)\]\s*')
decoder = json.JSONDecoder()
def apache_unescape(value):
    controls = {b'\\\\': b'\\', b'\\n': b'\n', b'\\r': b'\r',
                b'\\t': b'\t', b'\\v': b'\v', b'\\b': b'\b'}
    return re.sub(
        rb'\\(?:x[0-9a-fA-F]{2}|[\\nrtvb])',
        lambda m: bytes([int(m[0][2:], 16)]) if m[0][1:2] == b'x'
        else controls[m[0]],
        value.encode('utf-8'),
    ).decode('utf-8')

bad = 0
with open(sys.argv[1], encoding='utf-8', errors='replace') as source:
    for line in source:
        match = pattern.search(line)
        if not match:
            continue
        try:
            payload = line[match.end():].lstrip()
            if re.search(r'\[php[^\]:]*:[^\]]+\]', line[:match.start()]):
                payload = apache_unescape(payload)
            event, _ = decoder.raw_decode(payload)
            if not isinstance(event, dict):
                raise ValueError('event is not an object')
        except ValueError:
            bad += 1
            continue
        event['channel'] = match.group(1)
        print(json.dumps(event, ensure_ascii=False))
print(f'Unparsed event lines: {bad}', file=sys.stderr)
PY
```

При объединении файлов убирайте только доказанные дубли копирования. Совпадение
времени до секунды не означает один запрос. Цепочка SQL-ошибка → вывод сообщения →
`headers already sent` может породить много строк одного сбоя: сохраняйте первое
сообщение и причинную цепочку, а не только последнюю ошибку заголовков.

## 4. Сопоставить отказ сохранения с запросом и БД

1. Найдите на внешнем прокси `request_id`, время, путь, HTTP-код и upstream timing.
2. Найдите тот же ID в Apache и событиях приложения. Сопоставьте также
   `application_request_id`, если он записывается на прокси.
3. Для сохранения выпишите `testlogid`, `operation_id`, `expected_version`,
   `result_version`, статус и канал события.
4. Проверьте последующие запросы к тому же вопросу: был ли повтор и успешная запись.
5. Проверьте метаданные в БД в короткой транзакции только для чтения.

Внешний прокси должен **перезаписывать** входящий `X-Request-ID` своим значением.
ID для корреляции не является удостоверением личности. При отсутствии сквозного
ID сопоставление по времени/пути лишь предположение, которое отмечают в отчёте.

Пример для PostgreSQL в уже настроенном защищённом подключении: передайте в psql
`-v testlog_id=ЧИСЛО_ИЗ_ЖУРНАЛА`. Префикс таблиц замените, если он отличается.
Пароль не передавайте в командной строке.

```sql
BEGIN READ ONLY;
SET LOCAL statement_timeout = '5s';
SELECT l.testlog_id, l.testlog_testuser_id,
       l.testlog_answer_version, l.testlog_answer_saved_at,
       l.testlog_answer_operation,
       u.testuser_status, u.testuser_close_reason, u.testuser_last_activity
FROM tce_tests_logs AS l
JOIN tce_tests_users AS u ON u.testuser_id = l.testlog_testuser_id
WHERE l.testlog_id = :'testlog_id'::bigint;
ROLLBACK;
```

Запрашивайте небольшие списки конкретных ID; не выгружайте все ответы участников.
Текущее состояние БД не восстанавливает всю историю. Версия выше ожидаемой
подтверждает последующие изменения, но не тождество введённого текста. Пустое
текстовое поле не доказывает отсутствие ответа: выбор вариантов хранится также
в `tce_tests_logs_answers`. Проверка содержимого, если необходима, зависит от типа
вопроса и выполняется отдельно в закрытом контуре.

Для каждого случая укажите один из выводов:

- запись подтверждена событием успешного сохранения и метаданными БД;
- после отказа есть успешное сохранение того же вопроса; совпадение содержимого неизвестно;
- конкретный запрос отклонён до записи; результат последующих попыток указан отдельно;
- данных недостаточно: перечислены отсутствующие источники/события.

Если в БД нет подтверждения, а запрос не дошёл до записи, серверные журналы не
позволяют восстановить введённый в браузере ответ. Проверять черновик нужно отдельно;
нельзя объявлять ответ потерянным или сохранённым только по HTTP-коду.

## 5. Разобрать причины по отдельности

| Наблюдение | Что проверить |
| --- | --- |
| 403 | Причину `session_required`, `access_denied`, `csrf_failed` или `csrf_refreshed`, события auth, последующий повтор. Разные отказы требуют разной обработки; введённый ответ должен сохраняться в форме/черновике. |
| 409 | Ожидаемую и фактическую версии, параллельную вкладку/повтор операции, более позднее сохранение. Конфликт защищает новую версию от перезаписи. |
| 408 / 499 | Дошёл ли запрос до приложения, завершилась ли запись после обрыва связи, были ли повторы. |
| 502 / 504 | Точную причину из error log: отказ подключения, таймаут, `upstream prematurely closed connection`; затем рестарты, OOM, переключение слотов и настройки keepalive. Не увеличивать таймауты и не повторять POST автоматически без выяснения причины. |
| HTTP 200 с ошибкой | Файловые ошибки приложения и stderr: SQL/PHP-сбой мог быть выведен в HTML успешного HTTP-ответа. |
| 404 | Служебное сканирование (`/.env`, `/.git`), нужная иконка, ссылка текущей страницы, опечатка/обрезанный URL либо устаревший ресурс из кеша. |

Для 404 проверьте точный путь, метод, referer (если доступен), частоту и наличие ссылки
в текущем HTML и исходниках (`rg -n --fixed-strings 'имя-ресурса' public shared admin`).
Проверьте версию статических файлов и кеш браузера/service worker. Отсутствующая
иконка может действительно требоваться браузеру. Не восстанавливайте любой старый
JS и не превращайте все 404 в HTTP 200: сначала установите назначение ресурса.

## 6. Оформить результат и проверить исправление

Закрытый отчёт должен содержать:

1. Интервал UTC и локальное время, версию, источники и полноту сбора.
2. Сводку запросов/ошибок по уровням, доли отказов и задержки.
3. Причины с привязкой к исходным файлам и строкам.
4. Таблицу спорных сохранений: время, request ID, вопрос, причина, версии,
   последующий запрос, состояние БД, вывод и степень уверенности.
5. Отдельную классификацию 404 и список необходимых исправлений.
6. Необъяснённые случаи, недостающие данные и следующее действие.

После исправления повторите сбор за фиксированный интервал и проверьте целевой
сценарий на синтетическом участнике. Сравнивайте доли ошибок при сопоставимой
нагрузке, а не абсолютные числа разных интервалов. Ноль ошибок при отсутствии
запросов не подтверждает исправление. При выкладке собирайте оба слота согласно
[порядку обновления](blue-green-deployment.md), включая запросы, начатые до переключения.
В Git сохраняются процедура и обезличенные технические выводы; исходные материалы
и таблица участников остаются в закрытом каталоге.
