# Надёжное сохранение ответов

OpenVsoshCBT позволяет сохранить текущий ответ без перехода к другому вопросу.
Кнопка «Сохранить» показывает «Сохраняется…», а состояние «Сохранено» появляется
только после подтверждения базы данных сервером. При ошибке участник видит
«Не сохранено» и может повторить действие либо использовать обычную кнопку
подтверждения/перехода.

Обычная отправка формы сохранена как резервный сценарий для браузеров без
JavaScript или `fetch`.

Кнопки «Назад», «Далее», «Подтвердить» и переход из списка вопросов сначала
дожидаются подтверждения сохранения. После этого следующий вопрос загружается
из того же серверного обработчика без полной перезагрузки страницы. Сервер
по-прежнему формирует всю разметку вопроса: клиент не хранит правильные ответы
и не воспроизводит правила доступа. Если JSON-сохранение или загрузка вопроса
не удались до замены формы, выполняется обычная POST-отправка.

Если запрос не дошёл до сервера или сервер временно отвечает ошибкой 5xx,
страница хранит один снимок операции только в оперативной памяти и выполняет
до пяти повторов через 1, 2, 4, 8 и 16 секунд. Один и тот же ID операции
используется во всех повторах, поэтому потерянный HTTP-ответ не приводит к
повторной записи. Зависший запрос прерывается на клиенте через 15 секунд.
Текущий номер попытки и задержка показываются участнику.

Очередь намеренно не записывает ответы и CSRF-токены в `localStorage`,
`IndexedDB` или Service Worker. Она исчезает после закрытия страницы. При
изменении ответа во время отправки интерфейс снова показывает
«Есть несохранённые изменения», даже если более ранний снимок успешно записан.
Попытка закрыть страницу с несохранённым ответом вызывает стандартное
предупреждение браузера.

Старый механизм, который записывал текст эссе в `localStorage` и без проверки
версии подставлял его поверх ответа из базы, отключён. Уже существующие ключи
не читаются и не удаляются автоматически, чтобы обновление само по себе не
стёрло неподтверждённый пользовательский черновик.

## Защита от повторов и конфликтов

Каждая операция получает случайный 128-битный идентификатор. В журнале вопроса
хранятся последний идентификатор и монотонная версия ответа:

- повтор той же операции подтверждается без повторной записи;
- операция со старой версией получает HTTP 409 и не меняет ответ;
- проверка версии, обновление вариантов и фиксация новой версии выполняются
  в одной транзакции с блокировкой строки;
- endpoint принимает только POST, проверяет CSRF, владельца попытки, доступность
  теста и не кеширует ответ.

Fingerprint сессии использует только стабильные заголовки клиента. Заголовки
`Accept` и `Upgrade-Insecure-Requests` исключены, потому что они закономерно
отличаются у загрузки документа и `fetch`. Уже открытая сессия, созданная
старой версией, принимается один раз при обычной загрузке страницы и переводится
на новый fingerprint.

Oracle-адаптер в этой версии также сохраняет состояние транзакции и использует
`OCI_NO_AUTO_COMMIT` до явного `COMMIT` или `ROLLBACK`. Работу на Oracle всё
равно необходимо принять в отдельном окружении: штатные CI-тесты проекта
проверяют MySQL/MariaDB и PostgreSQL.

## Миграция существующей базы

До включения нового кода примените ровно один файл для своей СУБД:

- MySQL/MariaDB — `install/upgrade/mysql/openvsosh_answer_save.sql`;
- PostgreSQL — `install/upgrade/postgresql/openvsosh_answer_save.sql`;
- Oracle — `install/upgrade/oracle/openvsosh_answer_save.sql`.

Миграция добавляет в `tce_tests_logs` поля `testlog_answer_version` и
`testlog_answer_operation`. При нестандартном префиксе таблиц замените `tce_`
до запуска. Сначала сделайте полный дамп БД и проверьте миграцию на копии.

## Текущие ограничения

Если все повторы исчерпаны, участник должен восстановить связь и нажать
«Сохранить» ещё раз либо использовать обычную кнопку подтверждения.
Ответы и токены намеренно не сохраняются для автономной работы: полноценный
offline-режим требует отдельного подписанного пакета и в этот этап не входит.
