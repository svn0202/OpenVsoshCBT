# Журнал входов и отказов проверки формы

Приложение пишет JSON-события с префиксом `[openvsosh.auth]` через PHP `error_log()`.
В контейнерном проде они поступают в stderr Apache и журнал контейнера; отдельный
файл внутри сменяемого контейнера не создаётся. Хранение и ротация — у существующего
сборщика журналов. События появляются после выкладки этой версии, старые входы
восстановить таким способом нельзя.

События:

- `login.attempt` — обработка отправленных учётных данных началась;
- `login.succeeded` — аутентификация прошла;
- `login.rejected` — `authentication_failed`, `otp_failed` или `rate_limited`;
- `csrf.rejected` — `missing_token`, `malformed_token` или `token_mismatch`;
- `session.rejected` — `fingerprint_mismatch`.

Отказ CSRF может произойти до `login.attempt`. Событие `login.succeeded` означает
успешную проверку учётных данных, но не доказывает сохранение cookie браузером.
`authentication_failed` — общий отказ аутентификации, а не доказательство неверного
пароля: например, он возможен при ошибке обращения к БД. Альтернативные способы
входа без отправки обычной формы не покрываются событиями `login.*`.

Поля: время UTC, событие, причина, случайный ID запроса, метод, путь без query string,
IP из `REMOTE_ADDR`, ограниченный по длине User-Agent, введённый логин и признак наличия
cookie сессии. ID общий для событий одного запроса. Логин — введённое пользователем
значение, не доказательство личности. IP зависит от доверенной настройки proxy на
веб-сервере; приложение не доверяет произвольному `X-Forwarded-For`.

Пароли, OTP, CSRF-токены, значения cookie и содержимое сессии не записываются.
У события CSRF вне формы входа логин может быть пустым. Несовпадение токена пока
не различает смену сессии, страницы или заголовков браузера.

Пример поиска на сервере приложения:

```sh
sudo journalctl -u openvsoshcbt.service --since '30 minutes ago' --no-pager \
  | grep -F '[openvsosh.auth]' \
  | grep -E 'st980251|st1118577'
```
