# Связь запросов и сохранений ответа

Реализация в репозитории; для сквозной корреляции требуется выкладка PHP,
конфигурации контейнерного Apache и двух файлов Nginx. Работающий Nginx проверен
чтением конфигурации 12 сентября 2026: ранее этих директив в нём не было.

## Какие данные связаны

- Nginx создаёт `$request_id`, заменяет входящий `X-Request-ID` и передаёт его
  через host Apache в контейнер. В ответе участнику возвращает этот же ID.
- PHP принимает только 32 строчных hex-символа; при отсутствии корректного ID
  создаёт локальный. Это идентификатор для поиска, не авторизация. Публичный
  обход edge-прокси позволяет клиенту выбрать корректный ID, поэтому доверие
  к его происхождению обеспечивается сетью и заменой заголовка на edge.
- Авторизация, API, транзакция записи и финальное сохранение используют один ID.
  JSON API содержит его при успехе и отказе; обычный контроллер — в HTTP-заголовке,
  а финальный JSON — также в теле.
- `[openvsosh.answer]`: причина, HTTP-статус, заявленные ID теста/вопроса,
  версия и валидный ID операции. До проверки доступа это входные идентификаторы,
  а не подтверждение принадлежности вопроса участнику.
- `[openvsosh.answer.write]`: ID теста/вопроса, операция, ожидаемая версия,
  результат и длительность операции записи. `result_version` — версия после
  подтверждённого COMMIT или обнаруженная при конфликте; при ошибке `null`.
- `[openvsosh.answer.final]`: результат последнего сохранения с тем же ID запроса.
- Существующие поля БД `testlog_answer_version` и `testlog_answer_operation`
  связывают журнал с текущей записью. История ответов в БД этим изменением не создаётся.

Один повтор HTTP получает новый request ID, сохраняя ID операции при идемпотентном
повторе API. Поэтому запросы группируют по операции, а отдельный проход через
прокси ищут по request ID. Успешная запись в журнале не доказывает доставку
подтверждения браузеру. Для 499 возможна успешная запись с потерянным подтверждением.

В новых журналах нет текста ответа, cookie, токенов, query string или тела запроса.
Существующий журнал авторизации сохраняет прежний набор полей.

## Подключение Nginx

1. Установить `docker/production/vsosh-request-log.conf` в
   `/etc/nginx/conf.d/vsosh-request-log.conf` (контекст `http`).
2. Установить `docker/production/vsosh-request-location.inc` в
   `/etc/nginx/snippets/vsosh-request-location.inc`.
3. В `/etc/nginx/sites-available/vsosh.irro.ru.conf`, **внутри существующего
   `location /`**, рядом с `proxy_set_header`, добавить:

   ```nginx
   include /etc/nginx/snippets/vsosh-request-location.inc;
   ```

4. Проверить `nginx -t`, затем выполнить согласованную выкладку/reload.

Сниппет рассчитан на прочитанный текущий vhost. Сохраняется `/var/log/nginx/access.log`,
добавляется JSON-lines журнал `/var/log/nginx/vsosh-request.log`. Проверить, что
локальная logrotate-конфигурация охватывает новый `.log`.
Если конфигурация изменится, учитывать наследование `add_header` и `access_log`:
наличие этих директив в location заменяет унаследованные директивы соответствующего
типа. В прочитанном vhost дополнительных унаследованных `add_header` не обнаружено.

В образе Apache добавлен отдельный формат `openvsosh_request` в stdout:
входящий и исходящий ID, метод, путь, статус, длительность в микросекундах.
Промежуточный host Apache должен передавать `X-Request-ID` без замены.

## Проверка после выкладки

Сохранить синтетический ответ и взять `request_id` из JSON/HTTP-заголовка.
Найти его в `/var/log/nginx/vsosh-request.log` и PHP/container logs.
Поля Nginx `request_id` и `application_request_id` должны совпадать; затем
сопоставить событие `write` с ID операции и версией в БД.
Время upstream и статусы оставлены строками: Nginx может записывать `-` и
несколько значений при повторном обращении к upstream.

Повторить на стенде с 403, 409 и обрывом после записи. При 403 до транзакции
события `write` не должно быть. При обрыве до получения заголовков
`application_request_id` может быть пустым, но PHP-событие ищется по входящему ID.

Локальные проверки: `test/request_correlation_regression.py`, `test/AnswerSaveTest.php`,
`test/AuthLogTest.php`, проверки API и финального сохранения. Проверяют единый ID,
фильтрацию некорректного заголовка, отсутствие секретов и версии фактической записи.
